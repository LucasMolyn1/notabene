# Versionnement de l'API

L'API REST est servie sous `/api/v3`. Les versions et leur état sont publiés sur `GET /api/versions`.

## Règles

- **La version courante est figée** : seuls des ajouts compatibles (nouveaux champs, nouvelles routes) y sont faits. Aucun champ n'est supprimé ni renommé.
- Une rupture de compatibilité crée une nouvelle version majeure (`/api/v4`…) montée à côté de la précédente.
- Quand une version est remplacée, elle passe en `deprecated` : les réponses portent les en-têtes `Deprecation` et `Sunset`, avec un préavis d'au moins 6 mois.
- Les jetons d'API, les portées et le contrôle d'accès sont communs à toutes les versions : une version ne peut pas élargir les droits d'un jeton.
- Le point d'accès MCP (`/mcp`) et l'authentification (`/auth/*`) ne sont pas versionnés par préfixe.

## Versions

| Version | État | Contenu |
| --- | --- | --- |
| v1 | **retirée** | Première version (listes non paginées, `baseVersion`). |
| v2 | **retirée** | Pagination par curseur, `ETag`/`If-Match`, erreurs RFC 9457. Reprise par la v3. |
| v3 | stable (seule servie) | Tout v2, plus commentaires de page, permissions fines par page et notifications. |

v1 et v2 répondent 404. GraphQL (envisagé pour la v3) n'est pas fourni. Le client web et le serveur MCP utilisent la v3.

### Ce que la v3 a changé par rapport à l'ancienne v1

- `GET /pages` et `GET /search` renvoient `{ "items": [...], "nextCursor": "..." | null }`. Paramètres : `limit` (1 à 200, défaut 50), `cursor` (opaque, à renvoyer tel quel). Filtres de `/pages` : `spaceId`, `parentId` (identifiant ou `root`), `q` (titre), `updatedAfter` (millisecondes). La recherche est limitée à 500 résultats. Un curseur invalide donne 400.
- `GET /pages/:id` renvoie l'en-tête `ETag` (la version de la page, entre guillemets).
- `PATCH /pages/:id` : `If-Match` est **obligatoire pour modifier le contenu** (sinon 428) ; s'il est périmé, 412. Le titre et l'icône se modifient sans `If-Match`. Le champ `baseVersion` n'existe plus.
- Erreurs au format `application/problem+json` (RFC 9457) : `type`, `title`, `status`, `detail`, `instance`, plus `code` et `errors` (validation) ou des extensions (par exemple `version` pour un conflit). v1 garde son format `{ error, message }`.
- Nouveaux évènements de webhook : `page.permissions`, `comment.created`, `comment.updated`, `comment.deleted`.

### Ajouts de v3

- Commentaires : `GET|POST /api/v3/pages/:id/comments`, `PATCH|DELETE /api/v3/pages/:id/comments/:cid`. Fils à un niveau (réponse à un commentaire de premier niveau), résolution d'un fil, suppression logique. Écrire demande la portée `write` ; seul l'auteur modifie son texte ; l'auteur ou un administrateur supprime. Le texte est brut : le client doit l'échapper à l'affichage.
- Permissions par page : `GET /api/v3/pages/:id/permissions` et `PUT` (administrateur). Dès qu'une page a des entrées `{ userId, level: read|write }`, elle et ses sous-pages sont réservées à ces utilisateurs (la page restreinte la plus proche gouverne) ; les administrateurs voient tout. Une page restreinte est introuvable (404) pour les autres, y compris en liste, recherche, export, recherche IA et flux d'évènements, **dans toutes les versions** : la restriction vit dans le contrôle d'accès commun. Le niveau ne fait que restreindre : un lecteur n'écrit jamais, un niveau `read` empêche d'écrire malgré un rôle éditeur.
- Notifications : `GET /api/v3/notifications` (curseur, `unread=true`), `GET /notifications/unread-count`, `POST /notifications/read` (`ids` ou `all`), `GET|PUT /notifications/preferences`, `GET|PUT|DELETE /pages/:id/watch`. On suit une page en la créant, en la commentant ou à la main. Notifié : les suiveurs (hors auteur) d'un commentaire ou d'une modification, et l'auteur d'un commentaire auquel on répond. Les modifications se regroupent en une notification non lue par page ; l'e-mail (si SMTP et si la personne l'accepte) ne contient que le titre, l'auteur et un lien, et au plus un par heure et par page pour les modifications. L'accès à la page est revérifié à l'envoi et à la lecture : une page devenue restreinte ne notifie plus et disparaît de la boîte de réception. Temps réel : évènement SSE `notification` envoyé à son seul destinataire.
- Bases (ajouts compatibles) : colonnes `relation` (`config: { targetId, twoWay? }`, cellule = identifiants de lignes ; lecture limitée aux lignes d'une base que le lecteur peut lire) et `rollup` (`config: { relationId, targetPropertyId?, fn }`, calculé par le serveur) ; `config` sur chaque colonne ; `parentId` et `blockedBy` sur chaque ligne ; `settings` et `PATCH /bases/:id/settings` ; vue `timeline`. `PATCH /bases/:id/rows/:rowId` garde la ligne à la racine de la réponse et ajoute `row` (la même) et `shifted` (lignes décalées par les dépendances).
- Bases, calendrier et tâches (ajouts compatibles) :
  - vue `calendar` : `config.mode` (`month` par défaut, ou `week`), `config.dateId` et `config.endId` facultatifs (colonnes Date distinctes de la base, sinon 400). À défaut : colonne de début des réglages (puis première colonne Date) et colonne de fin des réglages. Une colonne supprimée disparaît de la vue ;
  - flux iCalendar en lecture par adresse secrète : `GET /bases/:id/ical` (`{ available, active, createdAt }`, jamais l'adresse), `POST /bases/:id/ical` (crée, ou change l'adresse si le flux existe : `{ url }`, montrée une seule fois ; 201 puis 200), `DELETE /bases/:id/ical` (révoque). Droit d'écriture sur la base ; état et création en session web seulement (403 par jeton d'API), révocation aussi par jeton d'API de portée `write` ; partage public activé pour l'instance et l'espace (403 sinon). Base restreinte : `POST` demande `{ confirmRestricted: true }` (sinon 409, `code: 'restricted'`), sauf si le flux a déjà été confirmé pour la même restriction. Lecture sans compte, hors `/api/v3` : `GET /ical/<jeton>.ics` (`text/calendar`), 404 uniforme dès que le partage public est coupé, que la base est à la corbeille ou que sa restriction a changé depuis la création. Contenu : par ligne datée, un identifiant, les dates (fin exclusive) et le titre, rien d'autre ; 2000 événements au plus. Le jeton n'est stocké que sous forme d'empreinte, n'est ni journalisé ni sauvegardé ; le flux disparaît avec la base (corbeille comprise), quand elle change d'espace, quand le partage public de l'instance ou de l'espace est coupé, et quand le compte qui l'a créé est désactivé ou supprimé ;
  - `GET /my-tasks` (portée `read`) : `{ tasks: [{ baseId, baseTitle, spaceId, rowId, title, due, status, done }], truncated }`, lignes où une colonne Personne désigne l'appelant, dans les bases qu'il peut lire. `?done=false` écarte les tâches terminées. Tri : en retard, échéance croissante, sans échéance. 200 bases parcourues et 500 tâches au plus (`truncated`) ;
  - `GET /bases/:id` ajoute `progress` : `{ propertyId, kind: 'status' | 'checkbox', done, total }` ou `null`. Terminé : dernière option de la première colonne Statut, sinon première case à cocher cochée.
- Bases, types de colonnes, modèles de ligne et graphiques (ajouts compatibles) :
  - nouveaux types de colonne : `url` (http ou https seulement, sans identifiants, normalisée, 2000 caractères au plus ; sans schéma, `https://` est ajouté), `email` (254 caractères au plus), `phone` (chiffres, espaces, `+ ( ) - .`, 5 à 30 caractères) ; valeur : texte. Toute autre adresse (`javascript:`, `data:`…), un caractère de contrôle ou un retour à la ligne donnent 400 ;
  - `created_time`, `updated_time` (valeur : `AAAA-MM-JJ` en UTC), `created_by`, `updated_by` (valeur : `{ id, name }`, seulement si l'auteur peut lire la base, sinon absente) : dérivées de la ligne, jamais stockées ; les écrire ou les effacer donne 400 ;
  - `unique_id` : `config: { prefix?: string | null }` à la création (8 caractères au plus : lettres, chiffres, tiret) ; la colonne présentée porte `config: { prefix, next }`. Valeur présentée : `"PREFIXE-N"` (ou `"N"`). Numéro attribué à la création de la ligne, jamais réutilisé (le compteur appartient à la base : supprimer puis recréer la colonne continue la numérotation), non modifiable (400, y compris `null`) ; une seule par base (409) ; l'ajout numérote les lignes existantes dans l'ordre ; seul le préfixe se modifie (`PATCH` de la colonne avec `config: { prefix }`) ; une copie de base renumérote à partir de 1 ;
  - `date_range` : valeur `{ start: 'AAAA-MM-JJ', end: 'AAAA-MM-JJ' | null }`, fin jamais avant le début. Peut servir de colonne de début des réglages (`endPropertyId` doit alors être `null`, sinon 400) et de `dateId` d'une vue calendrier (sans `endId`). Chronologie, calendrier, flux iCalendar, `GET /my-tasks` (échéance = fin, sinon début) et décalage des dépendances lisent le début et la fin de la plage ; une formule lit son début ; CSV : `AAAA-MM-JJ / AAAA-MM-JJ` ;
  - formules : `dateAdd(date, jours)`, `formatDate(date, "JJ/MM/AAAA")` (jetons `AAAA`, `MM`, `JJ`), `day(date)`, `weekday(date)` (1 = lundi), `listCount(prop("Sélection multiple"))`, `listHas(prop("Sélection multiple"), "option")`, `regexTest(texte, motif)`, `regexExtract(texte, motif)` (premier match ou `null`), `regexReplace(texte, motif, remplacement)` (remplacement littéral). Motifs : sous-ensemble linéaire (littéraux, `.`, classes, `\d \w \s \D \W \S`, `^ $`, `|`, groupes, `* + ?`), 100 caractères au plus ; pas de `{n,m}`, de référence arrière, de regard avant ou arrière, de quantificateur paresseux. Un motif écrit dans la formule est vérifié à l'enregistrement (400) ; un motif calculé invalide donne `null` ;
  - modèles de ligne : `GET /bases/:id` ajoute `rowTemplates: [{ id, name, values }]` (valeurs présentées comme une ligne) et `limits.templates` ; `POST /bases/:id/row-templates` `{ name, values }` (201), `PATCH /bases/:id/row-templates/:tid` `{ name?, values? }` (les valeurs reçues remplacent les anciennes), `DELETE` (204). Droit d'écriture sur la base ; 20 modèles par base (409) ; jamais de formule, cumul, relation, ID unique ni colonne dérivée (400). `POST /bases/:id/rows` accepte `templateId` (modèle de la même base, sinon 404) : valeurs du modèle encore valables pour l'appelant, puis `values` par-dessus ;
  - vue `chart` : `config.groupBy` (Sélection, Statut, Sélection multiple, Case à cocher, Date, Plage de dates, Personne, Texte, Créé par, Créé le), `chart` (`bar` par défaut, `line`, `donut`), `bucket` (`day`, `week`, `month` par défaut, `year` ; dates seulement), `metric` (`count` par défaut, `sum`, `avg`, `min`, `max`), `valueId` (colonne Nombre, Cumul ou Formule ; requis sauf `count`), `limit` (5 à 50, 20 par défaut), plus les `filters` existants. `GET /bases/:id/views/:viewId/chart` (lecture de la base, 60 par minute) : `{ buckets: [{ key, label, color?, value, count }], total, truncated, other?: { value, count } }`, calculé sur les lignes telles que le lecteur les voit, après les filtres de la vue ; `key` vaut `''` pour « Sans valeur ». Une vue qui n'est pas un graphique donne 400.
- Le client web propose la cloche, le suivi de page, les préférences, un panneau de commentaires par page et, pour les administrateurs, un écran de permissions par page. La co-édition en cours est coupée puis revérifiée au changement de permissions.

## Ajouter une version

1. Créer le dossier de routes de la version et l'enregistrer dans `server/src/app.ts` avec `prefix: '/api/vN'`.
2. Passer l'état de la version à `stable` dans `API_VERSIONS` (`server/src/routes/versions.ts`) et celui de la précédente à `deprecated` avec sa date `sunset`.
3. Réutiliser les fonctions de `server/src/lib/` : la logique métier et le contrôle d'accès ne sont jamais dupliqués par version.
4. Documenter les changements dans ce fichier et dans l'OpenAPI.
